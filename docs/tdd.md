# 生活情境雙語有聲故事書 TDD 開發規範

文件狀態：Active

## 1. 適用範圍

本規範適用於：

- **共用邏輯**：故事資料格式、頁數等於所選（4–10）／每頁 2 句／一對一繁中的驗證、輸入驗證（角色與情境不得只有空白、長度上限，以及頁數為 4–10 的整數）。
- **Worker API**：故事文字、單張封面兩類 `/api/*` 請求的參數檢查、轉送 OpenAI、逾時、錯誤對應（無效 key、權限不足、限流、網路、逾時），以及 key 不出現在回應與 log。
- **前端狀態邏輯**：生成狀態與素材狀態轉換、防重複提交、手動重試、新舊故事替換、播放狀態（同時只播一句、切頁停止並清除高亮、裝置無法朗讀時不可播放、單句出錯後回到可播放）。這些邏輯放在 composable 或純 TypeScript 模組中測試，不寫在元件 template 裡。

純 Vue 元件的視覺排版不強制執行 Red／Green 單元測試循環，改以本機實際操作與桌面／手機寬度手動驗收為主；但**凡涉及生成流程、失敗與重試、新舊故事替換與播放控制**的邏輯，必須抽離至 composable 或共用模組並依本規範執行 TDD（修正 UI 互動 Bug 時，仍須先補上能重現問題的狀態邏輯測試）。

## 2. 基本原則

所有功能開發與錯誤修正皆採用 TDD（Test-Driven Development），依序重複以下循環：

1. **Red**：先寫一個描述預期行為的測試，執行並確認測試因尚未實作該行為而失敗（若因型別或函式未定義而無法執行，需先補齊最小介面空殼，推進至「可執行但斷言失敗」才算完成 Red）。
2. **Green**：只撰寫足以讓測試通過的最小實作，不提前加入尚未被測試要求的功能。
3. **Refactor**：在測試持續通過的前提下整理程式碼、消除重複並維持前端、Worker 與共用模組的邊界，避免改變既有行為。

每次循環只處理一個小而明確的行為，完成後再進入下一個循環。

## 3. 最簡易實施規則

* 新增產品程式碼前，必須先有一個會失敗的測試。
* 修正 Bug 前，必須先新增一個能重現問題的回歸測試（Regression Test）。
* 測試應只驗證一個明確行為，名稱需能表達情境、輸入條件與預期結果。
* 測試必須可重複執行，且不應依賴測試順序、外部網路狀態或其他測試留下的狀態。
* **日常測試必須 100% 離線且零費用**：嚴禁在一般測試中呼叫真實 OpenAI API、使用真實 key 或連到已部署的 Worker；測試用 key 一律使用明顯的假值（例如 `sk-test-fake`）。
* **透過可注入介面隔離外部邊界**：
  * OpenAI：Worker 透過可注入的 `fetch` 或 client 呼叫 OpenAI，測試注入假回應，並能指定回傳 401／403／429、網路錯誤、逾時、格式錯誤或拒絕。
  * Worker API：前端測試注入假的 API client，可控制每個請求的成功、失敗與回應順序（例如舊故事的素材在新故事替換後才回應）。
  * 朗讀：注入可控制的假 `speechSynthesis`（可觸發 end／error 與無聲音情境），驗證播放、暫停與停止的呼叫，不實際發聲。
  * 時間與逾時：使用 fake timers 或注入時鐘，不以真實等待驗證逾時。
* **生成流程必須驗證成功、失敗與重試路徑**：文字與封面都要涵蓋成功、各類失敗、逾時與手動重試；失敗時須確認沒有發出不該有的素材請求、沒有自動重試、已成功內容不變、畫面沒有顯示成功。
* **Key 界線要有測試保護**：錯誤回應、log、故事資料與 URL 中不得出現測試送入的假 key；涉及新 API 或新錯誤路徑時補上對應測試。
* 優先使用快速的單元測試（共用邏輯與狀態邏輯）；Worker 的路由、請求轉送與錯誤對應加入對應的離線整合測試。
* 每次修改後執行相關測試；提交前必須執行完整離線測試、型別檢查與建置。
* 不得以刪除、略過（`it.skip`／`test.todo` 等）或放寬有效測試斷言的方式讓實作通過。

## 4. 基本驗證指令

測試框架為 Vitest（Node 環境，直接呼叫 Worker 的 fetch handler 並注入假 fetch，不啟動 workerd）；尚未選定 lint／format 工具。npm script 名稱以 `package.json` 為準，改變時同步更新本節。於專案根目錄執行：

```sh
npm test            # Vitest 完整離線測試（共用邏輯、Worker、前端狀態邏輯）
npm run typecheck   # vue-tsc --build：前端（含 .vue）與 Worker 的 TypeScript 型別檢查
npm run build       # Vite 建置，同時產出 Static Assets（dist/client）與 Worker
```

本機手動確認同網域路由與畫面時用 `npm run dev`（Vite＋workerd）或 `npm run preview`（建置後以 `wrangler dev` 執行）。改動 `wrangler.jsonc` 後執行 `npm run cf-typegen` 更新 `worker-configuration.d.ts`。

### 真實 OpenAI 試驗與部署驗收

真實模型輸出品質、帳戶權限、等待時間、Worker 部署環境的記錄設定與 HTTPS 行為無法以離線測試證明，依各 task 的驗收步驟執行（T0 前置驗證、T2–T4 真實生成、T5 部署驗收）：

* 每次真實 API 呼叫都由使用者的 key 計費；agent 先列出要送出的請求種類、次數與目的，取得使用者本次同意後才執行。
* key 由使用者以安全方式提供（例如當次 session 的環境變數或本機未追蹤的設定檔），不得寫入聊天、文件、測試、版本庫或試驗產出的 log。
* 試驗檔案與輸出完成後檢查沒有 key；可拋棄的試驗腳本不留在版本庫，除非 task 要求保留。
* Cloudflare 部署前取得使用者本次同意。Worker `kids-storybook-web` 已連接 GitHub（Workers Builds）：push 到 `main` 會自動執行 `npm run build` 與 `npx wrangler deploy`，部署到 `kids-storybook-web.cashwu.workers.dev`；其他分支產生預覽版本。因此請求 push 到 `main` 的同意時，須說明這也會部署正式網址。
* 結果（通過／不通過、真實或模擬、環境與實際觀察）記錄到 `PLAN.md` 第 5 節或該 task 的驗收紀錄；未執行時在收尾回報列為未執行，不宣稱已通過。

## 5. 完成條件

一項修改至少符合以下條件，才視為完成：

* 新增或調整的行為已有測試保護（生成流程已涵蓋成功、失敗、逾時與手動重試路徑）。
* 新增的測試曾先以預期原因失敗，完成實作後通過。
* 所有既有離線測試皆通過，且執行期間沒有發出任何真實網路請求。
* 型別檢查、lint（若已選定）與建置零錯誤通過。
* 測試程式碼、fixture、log、建置產物與文件中不含任何真實 key 或個人憑證。
* 未將 OpenAI 呼叫、key 處理或生成流程邏輯直接寫進 Vue 元件 template；Worker 未保存或記錄 key，未啟用付費請求的自動重試。
* 修改涉及產品行為、輸入／逾時邊界或技術選擇時，已同步更新 `PLAN.md` 與 `task.md`；需要真實 API 試驗、部署或手動驗收的項目已執行，或明確列為未執行。
